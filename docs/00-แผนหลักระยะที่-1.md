## ADR — ประเด็นรอการตัดสินใจ

ไฟล์แยกรายข้ออยู่ที่ `docs/adr/` (ดู `docs/adr/README.md`) — สรุปด้านล่างยังเป็นต้นทางความหมายตามแผนหลัก

### ADR-01: D-01 — Google Sheets เป็นฐานปฏิบัติงานหลักหรือเฉพาะต้นแบบ
**สถานะ**: เสนอให้รับรอง (รอผู้มีอำนาจระบุชื่อ/วันรับรองจริง)  
**ไฟล์:** `docs/adr/ADR-01-google-sheets-ฐานปฏิบัติงาน.md`

**ตัดสินใจ**: ระยะที่ 1 ใช้ Google Sheets เป็นฐานปฏิบัติงาน โดยออกแบบ Repository/Data Contract เพื่อย้าย PostgreSQL ได้ภายหลัง

**เหตุผล**:
- ต้นทุนต่ำ ตั้งค่าเร็ว ไม่ต้องรอ Cloud infrastructure
- ออกแบบ Repository Pattern ตั้งแต่ต้นเพื่อย้ายไป PostgreSQL ได้โดยไม่ต้องแก้ Business Logic

**ผลกระทบต่อข้อมูลบุคลากร/หน่วยงาน**:
- ข้อมูลบุคลากร/หน่วยงาน/ตำแหน่ง ต้องมาจากโครงการแยก `Dcg ฐานข้อมูลกลางบุคลากรและโครงสร้างองค์กร` เป็น Source of Truth
- Saraban เก็บเฉพาะข้อมูลนำเข้า/ภาพข้อมูล ณ เวลานั้น, สิทธิ์, และหน่วยงานที่เกี่ยวข้อง
- ห้ามสร้างข้อมูลบุคลากรซ้ำใน Saraban

**ผลกระทบต่อสถาปัตยกรรม**: ชั้นข้อมูล (`server/data/`) ต้องแยก Data Source ชัดเจน — อ่านบุคลากรจากกลาง, เก็บข้อมูล Saraban ในชีตเอง

**เงื่อนไข Phase 1**: ใน Phase 1 `personnel-source.ts` ใช้ Mock Contract เท่านั้น ห้ามเชื่อมฐานบุคลากรกลางจริงจนกว่าจะมีเจ้าของระบบ, วิธีเข้าถึง, Data Contract และสิทธิ์ที่อนุมัติแล้ว

### ADR-02: D-02 — วิธีเข้าสู่ระบบ
**สถานะ**: เสนอให้รับรอง (รอผู้มีอำนาจระบุชื่อ/วันรับรองจริง)  
**ไฟล์:** `docs/adr/ADR-02-วิธีเข้าสู่ระบบ.md`

**ตัดสินใจ**: ใช้ Google Workspace Authentication ในระยะที่ 1

**เงื่อนไข**: ต้องให้ฝ่าย IT ยืนยัน Domain และกลุ่มผู้ใช้ก่อนเปิดจริง

**ผลกระทบ**: Auth layer ออกแบบสำหรับ Google Workspace ก่อน; รองรับ SSO ได้ในอนาคต

### ADR-05: D-05 — เอกสารจำกัดการเข้าถึง/ลับ

### ADR-06: D-06 — การเชื่อมระบบสารบรรณเดิม

**สถานะ**: เสนอให้รับรอง (รอผู้มีอำนาจระบุชื่อ/วันรับรองจริง)  
**ไฟล์:** `docs/adr/ADR-07-ขอบเขตข้อมูล-ai.md`

**ตัดสินใจ**: ปิด AI สำหรับข้อมูลจริงใน Production จนกว่าจะมีนโยบายข้อมูลและการอนุมัติผู้ให้บริการ

**ผลกระทบ**: AI features (เช่น การช่วยร่าง) ทำงานเฉพาะบนข้อมูลตัวอย่าง/จำลองในระยะที่ 1; ไม่ส่งข้อมูลจริงผ่าน AI API

### แก้ไขที่ 5: Data Dictionary เป็นแหล่งจริงจุดเดียว + รองรับ Runtime
- `docs/data-dictionary.md` เป็นเอกสารต้นทางเชิงออกแบบ — แหล่งจริงเพียงจุดเดียวของ: ชื่อชีต, ชื่อคอลัมน์, ชนิดข้อมูล, บังคับกรอก/ไม่บังคับ, เจ้าของข้อมูล
- เมื่อมีการเปลี่ยนแปลงต้องรัน build/generate เพื่อสร้าง Schema Manifest ที่มี `รุ่นโครงสร้าง` และ `Header Hash`
- Apps Script ตรวจ Header Hash ของ Google Sheets กับ Schema Manifest ที่ถูก build แล้ว ไม่อ่าน Markdown ตอนรันงาน
- หากไม่ตรง ให้บันทึก Audit/แจ้งผู้ดูแล และหยุดอย่างน้อย: การเขียนข้อมูล, การออกเลข, การสร้าง PDF ควบคุม, และการทำงานตามเวลา (Trigger/Jobs) จนกว่าผู้ดูแลจะแก้ Schema แล้วผ่านการตรวจสอบ
- ห้ามแก้ทั้งสองฝั่งแยกกันด้วยมือ — ต้อง sync จาก Data Dictionary ไปยัง Schema Manifest เสมอ

---

### แก้ไขที่ 6: TypeScript เป็น Source of Truth
- ใช้ TypeScript เป็น source แล้ว build เป็น JavaScript สำหรับ Apps Script
- ต้องมี `tsconfig.json` และ build script ตั้งแต่ Phase 1
- Apps Script V8 ไม่รองรับ ES Modules โดยตรง ต้อง bundle เป็น IIFE หรือ CommonJS

### เกณฑ์จบ Phase 1

- Git repository พร้อมใช้งาน
- Project structure ตรงตาม `docs/08`
- **build, lint, type check และ test แบบจำลอง ผ่าน** (ไม่ใช่ `clasp push`)
- Repository Interface ออกแบบเสร็จ (Abstract ไม่ connect Sheet จริง)
- Data Dictionary ภาษาไทยเสร็จ เป็นแหล่งจริงจุดเดียวของชื่อชีต/คอลัมน์

## แผนงาน Phase 2-5 (คงเดิม ปรับเล็กน้อย)

### Phase 2: Backend Core (Data Layer)
- สร้างชั้นข้อมูลโดยใช้ Repository Interface จาก Phase 1
- ต่อ Google Sheets เมื่อมีสิทธิ์จริง
- สร้าง Audit Log layer

### Phase 3: Business Logic
- Workflow แก้ไขตามข้อปรับเชิงธุรกิจที่ 1 (ยกเลิก/ฉบับแทนที่เป็นเอกสารแยก)
- ห้ามเรียก L2 ว่า "อนุมัติ" — ใช้ "ออกเลข" หรือ "ตรวจขั้นสุดท้าย"

### Phase 4: Frontend
- UI ภาษาไทย 100%
- A4 Preview
- คิวกลาง แจ้งเตือน รายงาน
- หน้ารายละเอียดเอกสารแสดงความสัมพันธ์ฉบับเดิม/ฉบับแทนที่

### Phase 5: Testing & Release
- เกณฑ์ P95 และการทดสอบ 50/100/200 คน **คงไว้ในฐานะ "เกณฑ์ที่ต้องพิสูจน์ด้วยผลทดสอบ" ไม่ใช่คำรับประกันล่วงหน้า**
- ต้องผ่าน lint, type check, Unit Test, Playwright, Security/Secret Scan
- ต้องผ่าน Code Review, Staging, Human Approval ก่อน Production

## ข้อจำกัดและเงื่อนไข

1. **Phase 1 เริ่มได้ทันที** สำหรับงานที่ไม่พึ่ง Google Workspace จริง
2. **ห้ามสร้าง Google Sheets จริง, deploy clasp, เปิด AI API หรือแตะข้อมูลบุคลากรจริง** จนกว่าจะได้รับสิทธิ์และข้อมูลจากผู้รับผิดชอบ
3. **D-03 และ D-04** ยังต้องให้ผู้รับผิดชอบตัดสินจริง — Deferred บล็อกเฉพาะ SLA จริงและ Release Production
4. **Production ต้องผ่าน Human Approval** — ห้าม Deploy อัตโนมัติ
5. **ฟีเจอร์ที่ผ่านการรับรองเป็น Protected Baseline** — แก้ได้เมื่อมี Change Request
6. **ทุกงาน Phase 1 ต้องมี Task Manifest, Workflow, และ Skill Evidence** — ห้ามปิดงานโดยไม่มีหลักฐาน
7. **Data Dictionary เป็นแหล่งจริงจุดเดียว** — ห้ามซ้ำหรือขัดกับ Schema Manifest
8. **TypeScript เป็น source, build เป็น JavaScript** — ไม่ใช่ "ถ้าใช้"
9. **ยกเลิก/ฉบับแทนที่เป็นเอกสารแยก** — ฉบับเดิมคงเป็นหลักฐาน, ฉบับใหม่อ้างอิงกลับ
10. **personnel-source.ts ใช้ Mock Contract เท่านั้น** — ห้ามเชื่อมฐานบุคลากรกลางจริงใน Phase 1
11. **Data Dictionary ต้อง build เป็น Schema Manifest** — ห้ามแก้ทั้งสองฝั่งแยกกันด้วยมือ
12. **บันทึกการสำรองและกู้คืนข้อมูล ต้องรองรับ สำรอง / ทดสอบกู้คืน / กู้คืนจริง / ล้มเหลว**
13. **เมื่อ Header Hash ไม่ตรง ระบบต้องหยุดอย่างน้อย: การเขียนข้อมูล, การออกเลข, การสร้าง PDF ควบคุม, และการทำงานตามเวลา จนกว่าผู้ดูแลจะแก้ Schema แล้วผ่านการตรวจสอบ**
