## 2. สรุปหนึ่งย่อหน้า

Dcg Smart Saraban **ระยะที่ 1** คือเว็บแอปภาษาไทย 100% ช่วยร่าง ตรวจ ส่งคิวกลาง กลั่นกรอง 2 ชั้น ออกเลข สร้าง PDF ควบคุม ลงนามนอกระบบแล้วอัปโหลดกลับ — **รองรับหนังสือราชการครบ 6 ชนิดตามระเบียบ** และรองรับสถานะ **`ยกเลิก` / `ฉบับแทนที่`** โดยเก็บฉบับเดิมเป็นหลักฐาน ไม่ใช่ e-Signature และยังไม่แทนระบบสารบรรณเดิมทั้งหมด

แผนนี้เป็น **แผนดำเนินงาน** หลังแก้จุดขัดข้อกำหนด: ใช้ **Pilot ทางเทคนิค (หนังสือภายใน)** เป็น Vertical Slice แรกเพื่อพิสูจน์สถาปัตยกรรม แล้วขยายจนครบ 6 ชนิดก่อนปิดระยะที่ 1; โครงโค้ดเริ่มแบบ**จำลอง**ได้เมื่อมี ADR/ข้อเสนอชั่วคราว; **ห้าม deploy/Staging** จนกว่ามีสิทธิ์ Workspace; ความสามารถรองรับผู้ใช้ **2,000+** ต้อง**พิสูจน์ด้วยทดสอบ** ไม่ใช่สมมติว่าผ่าน; Backup/Restore Contract ออกแบบตั้งแต่ต้น และ**ห้าม Production ก่อน Restore Test ผ่าน**

## 4. ขอบเขตส่งมอบระยะที่ 1 vs Pilot ทางเทคนิค

### 4.1 ขอบเขตส่งมอบระยะที่ 1 (บังคับ — ห้ามตัด)

| หมวด | ต้องมี |
|------|--------|
| ประเภทหนังสือ | **ครบ 6 ชนิด:** ภายนอก, ภายใน, ประทับตรา, สั่งการ, ประชาสัมพันธ์, หนังสือที่เจ้าหน้าที่ทำขึ้นหรือรับไว้เป็นหลักฐาน |
| Workflow สถานะ | ร่าง → รอส่ง → รอกลั่นกรอง 1 → ส่งกลับแก้ไข หรือ รอกลั่นกรอง 2 → ออกเลขแล้ว → แนบฉบับลงนามแล้ว **และ** `ยกเลิก`, `ฉบับแทนที่` |
| ยกเลิก / แทนที่ | หลังออกเลข: ห้ามแก้ทับ; ยกเลิกหรือสร้างฉบับแทนที่ **เก็บฉบับเดิม + รุ่น + Audit เป็นหลักฐาน** |
| สิทธิ์ | RBAC Backend, แยกผู้กลั่นกรองชั้น 1 กับ 2 ของเอกสารเดียวกัน |
| ข้อมูล | ชั้น `data` ตาม Schema Manifest; อ่านคอลัมน์ตามชื่อไทย; UI ห้ามคุย Sheet ตรง |
| แจ้งเตือน | ศูนย์แจ้งเตือนในเว็บ (อีเมลไม่บังคับ) |
| รายงาน | แยกจำนวนเอกสารไม่ซ้ำ / ภาระงานกลั่นกรอง / ออกเลข / ยกเลิก-แทนที่ |
| Backup/Restore | Contract + Audit ตั้งแต่ต้น; ผ่าน Restore Test ก่อน Production |
| ทดสอบ | Unit + Playwright (เมื่อมี Staging) + Load/Concurrency/Soak ตามเกณฑ์พิสูจน์ขีดความสามารถ |
| ภาษา | UI/สถานะ/Error/Notification ภาษาไทย 100% |

### 4.2 Pilot ทางเทคนิค (ไม่ใช่ขอบเขตระยะที่ 1)

- **วัตถุประสงค์:** พิสูจน์สถาปัตยกรรม ชั้นงาน Lock ออกเลข Audit PDF คิว 2 ชั้น บนเส้นทางที่สั้นที่สุดที่ยังมีความหมาย
- **ชนิดหนังสือแนะนำ:** หนังสือภายใน (slice แรกเท่านั้น)
- **ทำได้:** demo ภายในทีม, ทดสอบจำลอง, ขยาย pattern ไปอีก 5 ชนิด
- **ทำไม่ได้:** ประกาศว่า “ระยะที่ 1 เหลือแค่ 1–2 ชนิด”, ปิดงานระยะที่ 1 โดยยังขาดชนิดใดชนิดหนึ่งตามแผนหลัก, ตัด `ยกเลิก`/`ฉบับแทนที่` ออกจากส่งมอบ

### 4.3 ลำดับขยายประเภทหนังสือ (หลัง Pilot)

1. หนังสือภายใน — Pilot / slice แรก  
2. หนังสือภายนอก  
3. หนังสือประทับตรา  
4. หนังสือสั่งการ  
5. หนังสือประชาสัมพันธ์  
6. หนังสือที่เจ้าหน้าที่ทำขึ้นหรือรับไว้เป็นหลักฐาน  

แต่ละชนิด: แม่แบบ + กฎตรวจจากค่าตั้งค่า/Schema (ห้าม hardcode) + unit/e2e อย่างน้อย 1 เส้นทาง + checklist ตาม `saraban-document-review`

## 5. ทิศทางสถาปัตยกรรม (แนะนำ)

### ทางเลือก A — Apps Script แยกชั้น + Repository (แนะนำระยะที่ 1 ตามเอกสารปัจจุบัน)

- Web App (`doGet`/`doPost`) แยก `server/*` + `client/*` ตาม `docs/08`
- ชั้น `data` abstract ตาม **Schema Manifest**; พร้อมสลับ storage (Sheets → PostgreSQL) โดย UI ไม่รู้เรื่อง storage
- **ไม่สรุปว่ารองรับ 2,000+ ผู้ใช้ได้บน Sheets** — ต้องพิสูจน์; ถ้าไม่ผ่านเกณฑ์ → แผนย้ายฐานข้อมูลเป็นงานบังคับไม่ใช่ทางเลือกสวย ๆ

### ทางเลือก B / C

- Hybrid Cloud หรือ PostgreSQL ตั้งแต่ต้น: พิจารณาเมื่อ ADR (D-01) หรือผล Load/Soak ยืนยันว่า Sheets ไม่เพียงพอ — รายละเอียดอยู่ในแผนหลัก/ADR ไม่ทับในแผนดำเนินงานนี้

## 6. ประตู (Gates) — ฉบับแก้

### Gate 0 — เริ่มงานโครงสร้าง/จำลองได้เมื่อมีหลักฐานข้อสมมติ

**ปลดล็อกเมื่ออย่างน้อยข้อใดข้อหนึ่งต่อประเด็นที่กระทบงาน:**

| ประเด็น | ขั้นต่ำที่ต้องมีก่อนแตะโค้ดส่วนนั้น | ไม่ต้องรอ |
|---------|-------------------------------------|-----------|
| D-01 Storage | **ADR หรือข้อเสนอชั่วคราว** บันทึกใน `docs/adr/` หรือ `docs/99` ว่าใช้ Sheets จำลอง + Repository interface | อนุมัติสุดท้ายจากผู้มีอำนาจ |
| D-02 Auth | **ADR/ข้อเสนอชั่วคราว** (เช่น session Web App / โหมดจำลองผู้ใช้ทดสอบ) | SSO จริง |
| D-07 AI | **ข้อเสนอชั่วคราว:** เลื่อน AI ออกจากเส้นทางหลัก หรือ mock เท่านั้นจนกว่ามีนโยบาย | นโยบายข้อมูลจริงครบ |

**อนุญาตใน Gate 0 หลังบันทึกข้อสมมติ**

- สร้างโครงโฟลเดอร์ `apps-script/`
- เขียน domain/data แบบ **in-memory / fixture / fake Sheet gateway**
- lint, typecheck, unit test จำลอง
- ร่าง Schema Manifest ให้สอดคล้องแผนหลัก 17 ชีต

**ห้ามใน Gate 0**

- เชื่อม Workspace จริง, deploy, `clasp push`, ใส่ secret/spreadsheet id ใน repo
- สรุปขีดความสามารถผู้ใช้โดยไม่ทดสอบ

### Gate S — สิทธิ์สภาพแวดล้อม (Environment Access)

**ปลดล็อกเมื่อ:** มีบัญชี Google Workspace + Apps Script project + สิทธิ์ Sheets/Drive สำหรับ**สภาพแวดล้อมทดสอบที่แยกจากข้อมูลจริง**

**จึงจะอนุญาต:** `clasp push` ไป Staging, ผูก Sheet ทดสอบ, Playwright ต่อ URL Staging, ทดสอบ Restore บนพื้นที่ทดสอบ

**ก่อน Gate S:** ทุกอย่างเป็น local/CI จำลองเท่านั้น

### Gate 1 — ก่อน UAT กลุ่มผู้ใช้จริง / ใกล้เปิดใช้

| รหัส | ขั้นต่ำ |
|------|--------|
| D-03 SLA | ค่าในชีตตั้งค่าที่รับรองหรือ ADR ชั่วคราวที่ใช้ UAT |
| D-04 RPO/RTO | รับรอง + **Restore Test ผ่านบน Staging** |
| D-05 เอกสารลับ | ยืนยันนอกสโคประยะ 1 หรือมีมาตรการรับรอง |
| D-06 ระบบเดิม | ยืนยันนอกสโคปหรือมี integration spec |

### Gate P — ก่อน Production

- ผ่าน CI, Staging, Code Review, Human Approval  
- **Restore Test ผ่าน** (บังคับ — ไม่มีข้อยกเว้น)  
- Backup Contract ทำงานหรือมี runbook + หลักฐานรอบทดสอบ  
- Load/Concurrency/Soak ตามแผนพิสูจน์ขีดความสามารถ — **รายงานผลจริง**; ถ้าไม่ผ่านต้องมี ADR ย้ายฐาน/ลดขอบเขตการเปิดใช้  
- Protected Baseline ของฟีเจอร์ที่รับรองแล้ว  
- หนังสือ **ครบ 6 ชนิด** + Workflow **ยกเลิก/ฉบับแทนที่** ผ่านเกณฑ์รับมอบ

### เฟส 1 — Scaffold โครง + คุณภาพจำลอง (ไม่มี Staging)

**เป้าหมาย:** โครงแยกชั้นตาม `docs/08` ที่ build และทดสอบได้**บนเครื่อง/CI** โดยไม่ต้องมี Workspace

```text

  appsscript.json          # โครง — ยังไม่ผูก deploy จริง

  client/...

  tests/e2e/               # เตรียมโครงได้ แต่ยังไม่บังคับรันต่อ URL จริง
```

| งาน | ผลลัพธ์ | ห้าม |

| CI ท้องถิ่น: lint, typecheck, unit | pipeline เขียวบน mock | ผูก secret |

### เฟส 6 — พิสูจน์ขีดความสามารถ + Hardening + เตรียม Production

#### 6.1 เป้าหมายองค์กรและความไม่แน่นอน

- มีผู้ใช้ในองค์กรระดับ **2,000+ คน**  
- **ยังไม่ทราบ** ปริมาณใช้งานต่อวัน / พร้อมกันสูงสุด  
- **ห้าม**เขียนในเอกสารปล่อยระบบว่า “รองรับได้หลักร้อย/หลักพัน” โดยไม่มีผลทดสอบแนบ  

#### 6.2 ชุดทดสอบบังคับ (พิสูจน์ ไม่ใช่การรับประกันล่วงหน้า)

| ชุด | จุดประสงค์ | ผลที่เป็นไปได้ |
|-----|------------|----------------|
| Load | เปิดงาน ค้นหา บันทึก ส่งคิว ภายใต้ภาระที่เพิ่มขึ้นเป็นขั้น | ได้กราฟ latency/error |
| Concurrency | ออกเลข / เปลี่ยนสถานะพร้อมกัน (อ้างอิงอย่างน้อยชุด 20 และขยายตามที่วัดได้) | ห้ามเลขซ้ำ ข้อมูลหาย สถานะข้าม |
| Soak | เดินระบบต่อเนื่องพร้อมรายงาน/backup จำลอง | หา memory/quota leak |
| Restore | กู้ตาม Contract บน Staging | ผ่าน/ไม่ผ่านเป็นเกณฑ์ Gate P |

ค่าใน `docs/05` (50/100/200, P95 ฯลฯ) = **เกณฑ์ตั้งต้นสำหรับออกแบบชุดทดสอบ** ไม่ใช่ใบรับรองว่าระบบผ่านแล้ว

#### 6.3 เมื่อผลทดสอบไม่ผ่าน

1. บันทึกผล + เปิดประเด็นใน `docs/99` หรือ ADR  
2. ทางเลือกบังคับพิจารณา: ปรับสถาปัตยกรรมชั้น data, **ย้ายฐานข้อมูล (เช่น PostgreSQL)**, จำกัดการเปิดใช้เป็นเฟส, เพิ่มคิว/สรุปข้อมูล  
3. ห้าม “ลด test ให้ผ่าน” หรือแก้เกณฑ์โดยไม่มีผู้อนุมัติ  

#### 6.4 อื่น ๆ ก่อน Gate P

- Security/Secret scan, OAuth scope ขั้นต่ำ  
- a11y พื้นฐาน + responsive ตาม DESIGN.md  
- Human Approval + แผนย้อนกลับ

## 9. Definition of Done ร่วม (ทุกงาน)

งาน**ห้ามปิด**ถ้าขาดข้อใดข้อหนึ่ง:

1. Task Manifest + Skill Evidence ใน `docs/agent-runs/`  
2. ระบุ WF-xx และ Skill ที่ใช้จริง  
3. ไม่ขัดแผนหลัก 17 ชีต / ADR / Schema Manifest  
4. ภาษาไทย 100% บนข้อความผู้ใช้  
5. Backend ตรวจสิทธิ์ — UI ไม่ใช่จุดตัดสิน  
6. ทดสอบตามความเสี่ยง; **เฟสก่อน Gate S = unit/จำลอง**; e2e ต่อ Staging หลัง Gate S  
7. ไม่แก้ test เพื่อให้ผ่านถ้า Spec ไม่เปลี่ยน  
8. ไม่มี secret / spreadsheet id อ่อนไหวใน git  
9. งานที่แตะเลขหนังสือ สถานะ PDF ยกเลิก แทนที่ Backup → มี test ที่เกี่ยวข้อง  
10. งานที่แตะการปล่อย Production → ตรวจ Restore Test และผลพิสูจน์ขีดความสามารถ

## 10. Backup / Restore Contract (ขั้นต่ำตั้งแต่ต้น)

ออกแบบและอ้างอิงในโค้ด/docs ตั้งแต่เฟส 0–2 แม้ job เต็มรูปแบบอยู่เฟส 5:

| รอบ | วัน (เปลี่ยนแปลง), สัปดาห์ (เต็ม), เดือน (export ระยะยาว) — ค่าละเอียดตาม D-04 เมื่อรับรอง |

| เกณฑ์ Production | Restore Test ผ่านภายในรอบที่กำหนด (อย่างน้อยหลักฐานหนึ่งรอบก่อน Gate P) |
